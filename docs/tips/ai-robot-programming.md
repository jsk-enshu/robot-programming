# AI と一緒に実機のプログラムを作る（例：ルービックキューブを掴む）

床に置いたルービックキューブを，Jedy が手で掴んで持ち上げるプログラムを，AI と相談しながら作った記録である．
一度で動いたわけではない．何度も失敗し，そのたびに「何が起きているか」を人と AI で確かめながら進めた．
その流れ自体が，実機のプログラムを作るときのやり方の見本になるので，失敗も含めてそのまま載せる．

AI との進め方は 2 通りある．どちらでも，**AI ができないこと (実物を見る・触る・安全を判断する) は人がする**．

| | A. AI TA に相談しながら自分で書く | B. AI エージェントに実機を任せる |
| --- | --- | --- |
| プログラムを書く・実行する | 自分 | AI (人が許可する) |
| AI の役目 | 相談相手．考え方・コード・確かめ方を提案する | 書いて，動かして，測って，結果を報告する |
| 人の役目 | 書いて，動かして，確かめる | 方針を決める．実物を見て伝える．危ないときに止める |
| 演習では | AI TA ({doc}`ai-ta`) | 研究室などで Claude Code のようなエージェントを使うとき |

## 経緯（失敗も含めて）

### 1. 最初のプログラム：手が届かない

キューブは物体の認識 (`ri.what_do_you_see(["rubik's cube"])`) と深度で見つけ，逆運動学 (IK) で手を持っていく．
2 日目の `grasp_tag` (台の上の立方体を横から掴む) をまねて手を水平にすると，**床の高さにはどこにも手が届かなかった**
(モデルで，前方 0.14〜0.26 m のどの位置も IK が解けない)．
そこで手を斜め下に傾けて上から近づけることにした．傾きを 90° (真下) から 15° まで試し，解けた中でいちばん急なものを使う．

### 2. 失敗：手が目標から 8〜10 cm 外れる

<video width="100%" controls preload="metadata" poster="../fig/jedy-ai-grasp-fail.jpg">
  <source src="../fig/jedy-ai-grasp-fail.mp4" type="video/mp4">
  お使いのブラウザは動画タグをサポートしていません．
</video>

**動画：** 右手で掴もうとして失敗したところ (2 倍速)．キューブの上までは来るが，入れる段階で手が前に伸び，目標から 82 mm の所で止まる．

IK は解けていて，プログラムもエラーなく最後まで進んだ．それでも掴めない．ここからは「どこが思ったとおりでないか」を 1 つずつ確かめた．

### 3. 「D405 で位置はちゃんと出ている？」

深度を使わない方法と比べた．認識の枠の下端の画素を通る光線と床の交点 (`pixel_on_floor`) は，キューブの前の下端になるはずである．

| | 前 x [m] | 横 y [m] | 高さ z [m] |
| --- | --- | --- | --- |
| D405 (深度) で出した点 | 0.128 | −0.068 | −0.072 |
| 色の画像だけで出した前の下端 | 0.116 | −0.078 | −0.116 (床) |

D405 の位置は 1 cm ほどで合っていた．ただし高さが床から 4.4 cm で，**測った点はキューブの上の面**だった (首を下に向けて上から見ているため)．
プログラムはこれを「前の面」だと思い込んで，中心を 1〜1.5 cm 奥にずらしていた．

### 4. RViz で点群と箱を出して確かめる

{ref}`show-3d` で，点群・認識した箱・プログラムの目標を重ねて表示した．

```{figure} ../fig/jedy-ai-object-box-rviz.jpg
---
name: fig:jedy-ai-object-box-rviz
---
点群 (D405) の中のキューブに対して，緑の箱 (1 点から奥にずらしたもの) はずれている．
青の箱 (枠の中の深度の点から作った箱) は点群のキューブを包んでいる
```

人から「jsk_pcl_ros の `ClusterPointIndicesDecomposer` にあるような，PCA や床にそろえた箱にできないか」という提案があり，
`jedy_vision.object_box()` を作った．枠の中の深度の点を base_link に移し，床の点を除き，床に立てた向き付きの箱にする．
向きは，細長い物なら PCA の主軸，正方形に近い物 (キューブ) なら点を囲む面積最小の長方形の辺から決める (正方形は PCA では向きが決まらない)．
中心は 0.139 m になり，色の画像だけで出した値 (前の下端 0.116 m + 大きさの半分 2.3 cm) と一致した．

### 5. それでも掴めない → IK の姿勢を絵で見る

箱を直しても，また手が目標から 98 mm の所で止まった．人から「IK を解いた姿勢を見せて」と頼まれ，
PyrenderViewer で，計画した姿勢をキューブと一緒に描いた．

```{figure} ../fig/jedy-ai-ik-poses.jpg
---
name: fig:jedy-ai-ik-poses
---
IK で解いた姿勢 (赤い箱がキューブ，細い軸が手の目標)．左上から，実機の今の姿勢，腕を上げた姿勢，上・手前・掴む・持ち上げる
```

キューブが台車のすぐ前 (0.14 m) にあるため，右腕は**前腕を体の正面に折りたたむ姿勢**になっていた．
IK は手の位置と向きしか見ておらず，腕が自分の台車に当たることは考えていない．
また，実機の今の姿勢 (左上) では右腕が体の前で交差していて，送ったはずの姿勢と違っていた．

### 6. 実機に姿勢を送って，関節ごとに比べる → 右腕の不調

「掴む直前の姿勢を実機に送ってみて」．送った角度と，サーボが測った角度を関節ごとに比べた．

```{figure} ../fig/jedy-ai-right-shoulder-stuck.jpg
---
name: fig:jedy-ai-right-shoulder-stuck
---
右肩が前に上がったまま動かず，腕が前に水平に突き出している
```

| 関節 | 送った角度 | 測った角度 |
| --- | --- | --- |
| `rarm_joint1` (右肩) | +29.0° / −54.1° / 0.0° | **−94.4° / −92.5° / −92.5°** |
| ほかの 6 関節 | | 送った角度から 1° 以内 |

**右肩のサーボだけが，何を送っても −92° 付近から動かなくなっていた**．
その日の昼には普通に動いていたので，掴む試行の途中 (腕が台車に当たったとき) に何かが起きたと考えられる．
手で見て確かめるのは人の仕事である (下の「人がしたこと」)．

### 7. 「右に回って左手で取れない？」→ 成功

右腕を使わずに，台車を右に約 60° 回し，キューブを左側に持ってきて左手で掴んだ (一番上の動画)．
キューブは中心 [0.159, 0.042, −0.097] m (少し遠く，斜めの位置) で，左腕は無理のない姿勢で届いた．
腕を動かすたびに関節の送った角度と測った角度を比べ，15° 以上ずれたら止めるようにしてある (最大 7.5° だった)．
グリッパは −0.10 rad で止まり (何も掴まないと約 −0.39 rad)，動画でもキューブが床から浮いている．

このとき分かったことは，サンプル `ros2 run jedy_vision grasp_object` に入れてある
(`object_box` で位置と向きを出す，急な傾きから試す，関節が 15° 以上ずれたら止める)．
ただし，**自分の体との衝突はまだ調べていない**．キューブが台車に近すぎるときは，少し下がってから使うこと．

## 人がしたこと

AI は画像・数値・ログから考えることはできるが，次のことはできない．今回も人がした．

- **安全の判断**：動かす前に周りを見る．腕や台車が動くときにそばにいて，危なければ止める・電源を切る．
- **実物を見る・触る**：ケーブルの抜け (首のサーボが応答しなかった)，USB アダプタの挿し直し，右肩のサーボの不調を手で確かめる．
- **アイデアを出す**：「jsk_pcl_ros のように PCA で」「IK の姿勢を見せて」「右に回って左手で」は，どれも人の提案だった．
- **やめどきを決める**：動かない原因が実物の故障なら，プログラムを直し続けても解決しない．TA や教員を呼ぶ．

## A. AI TA に相談しながら自分で書く

演習では AI TA ({doc}`ai-ta`) が使える．上の流れを自分でたどるなら，たとえば次のように相談する．

```{code-block} console
$ ta 'ルービックキューブを床から掴むプログラムを作りたい．ri.what_do_you_see と深度で位置を出して IK で手を持っていく方針でよい？'
$ ta 'IK は解けるのに手が目標から 8 cm 外れる．何を確かめればよい？'
$ ta review ~/enshu/grasp_cube.py     # 実機で動かす前に
$ ta fix                               # エラーが出たら
```

AI TA の答えは仮説である．確かめるのは自分で，そのための道具は資料にある．

- 位置が合っているか：{ref}`show-3d` で点群と箱を重ねる
- IK の姿勢：PyrenderViewer で解いた姿勢を描く ({doc}`skrobot-workflow`)

```{code-block} python
from jedy_skrobot import connect
from skrobot.viewers import PyrenderViewer

robot, ri = connect(load_meshes=True)
viewer = PyrenderViewer()
viewer.add(robot)
viewer.show()
robot.angle_vector(planned)     # IK で解いた姿勢 (angle_vector)
viewer.redraw()                 # 送る前に，腕が体や床に当たらないかを目で見る
```

- 実機がその姿勢になったか：送った角度と測った角度を関節ごとに比べる

```{code-block} python
import numpy as np
ri.angle_vector(planned, 3.0)
ri.wait_interpolation()
for j, sent, got in zip(robot.joint_list, planned, ri.angle_vector()):
    if abs(np.rad2deg(got - sent)) > 5:
        print(j.name, 'sent', np.rad2deg(sent), 'measured', np.rad2deg(got))
```

うまくいかないときは，やりたいこと・試したこと・起きたことを AI TA に文章で説明してみる．
説明するだけで自分で気づくことも多い ({ref}`confessional-debugging`)．

## B. AI エージェントに実機を任せる

今回は，Claude Code (AI エージェント) が PC 上でプログラムを書き，人の許可を得て実機を動かし，
カメラ・関節角度・ログ・動画から結果を確かめて報告した．人は上の「人がしたこと」を担当した．
任せるときに大事だったこと：

- **動かす前に，何をするかを聞く**．腕・台車がどう動くか，どこに当たりうるかを説明させてから許可する．
- **見張りを入れさせる**．関節が送った角度から大きくずれたら止める (今回は 15°)．壊れる前に止まる．
- **証拠で報告させる**．「成功した」ではなく，動画・RViz の画像・関節角度の表で見せてもらう．
- **PC を重くしすぎない**．認識・RViz・録画を同時に動かしすぎると，サーボを動かすプロセスが周期に間に合わなくなり，
  一度止まった (サーボのトルクが切れ，腕が落ちる)．
- **故障を疑うのは人**．AI は「この関節だけ指令に追いついていない」までは突き止められるが，サーボを手で確かめることはできない．
- **倒れないかを考える**．このあと，右肩が動かないまま (右腕が前に水平に伸びたまま) 左腕を大きく外に振り出したところで，Jedy が横に倒れた．
  プログラムは転倒に気づかず先へ進んでいた．腕を大きく動かすときは重心を考え，動かしている間は人が見ていること．
